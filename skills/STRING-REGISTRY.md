## Whole-name replacements (2026-10-07)

For an item-name stream, compare the entire rendered stream including `<f800>`
before counting substrings. `Recovery Potion` → `Potion` is a valid shorter
replacement even though the new word occurs inside the old name. Keep the

`generated/change-ledger.csv`'s planning role, and `docs/HANDOFF.md` §4/§4a's hand-written tables. It is the ONE

## Go registry progress report (2026-10-20)

`registry_status` in `tools/go` pins registry, glossary, milestone flow and one
plain Markdown template. It reuses the guarded raw reader and exclusive publisher;
Go computes counts while the template owns presentation. Preserve exact flow VMA
spellings and source-order diagnostic IDs. Missing status/provenance becomes
unknown; explicit null remains distinct. Other group nulls become unknown.
An explicit recipe date replaces the old local clock; escaping and visibility of
all provenance buckets are deliberate presentation changes. This describes plan
facts, never installed content. See `tools/go/README.md` for bounds and invocation.

## Go registry CSV projection (2026-10-20)

`registry_export` in `tools/go` shares the pinned raw registry reader and exclusive
new-output publisher. Ordered `registry_columns` are recipe data; preview reports
rows/hash, apply creates a new CSV. The exporter preserves embedded CR/LF while
using CRLF records: Go CSV CRLF mode rewrites cell text and cannot substitute
for this byte contract. Selected flat strings/null/integers/booleans are supported;
selected floats/containers refuse. This is the registry plan, never disc truth
or the glossary/flow status report. See `tools/go/README.md`.

## Go draft-row import (2026-10-20)

`tools/go` now accepts reviewed draft rows through `registry_add`, using the same
pinned registry snapshot and exclusive new-output publisher as its other registry
operations. IDs are table keys; matching existing JP/EN preserves all row metadata,
and all-present batches preserve exact source bytes/date. Only genuinely new rows
must start as drafted. This is a data-import lifecycle, not glyph/marker/fit or
reference validation. See `tools/go/README.md` and
`tools/go/evidence/registry-add-proof.json`; the canonical registry is not rewritten.

## Reference: canonical text markup (`jp`/`en` fields)
Adopted from `generated/change-ledger.csv`'s already-proven, machine-decoded convention (retires
`docs/HANDOFF.md`'s old `\|`/`//` prose convention):
- `|` — a hard line break WITHIN a page (glyph code `0x0800`).
- `//` — a page break (glyph code `0x1000`).
- `[spk 0xNNNN]` — prefix on a page whose speaker differs from the previous page's.
- `{{HL:0xNNNN}}` / `{{PARAM:0xNNNN}}` — added 2026-09-01: inline position markers for
  `standalone_codes`/`param_blocks` (see schema above). Not glyph text — a patch tool must recognize
  and specially handle these tokens, never encode them as literal characters.

**`en` can carry pre-authored, previously-unconsumed `{{HL:0xNNNN}}...{{HL:0xNNNN}}` phrase-wrap markup — fixed 2026-09-08.** Some entries' `en` fields already had this convention written by earlier authoring passes (`tools/add_event_taunt_title_entries.py`, `tools/add_cluster2_entries.py`, e.g. `0x4efb40` "Maconde": `{{HL:0xb001}} Maconde{{HL:0xb008}}`) marking which phrase should carry the JP source's own `standalone_codes` highlight — but `encode_stream()` hard-refused ANY `en` containing `"{{"`, so this real, already-translated content silently sat un-encodable rather than flagged as a translation gap. Fixed via `tools/text_encoder.py`'s `encode_label()` (generalized from a single-word-only 2026-09-04 mechanism to multi-word, punctuation-tolerant phrase wrapping) plus new `derive_en_hl_markup(en_text, jp_tokens)`, which parses the `{{HL:}}` markers, structurally validates their in-order code-value sequence against the JP source's own hl codes, and emits a clean plain `en` plus a ready `hl_wraps` list — raising `MarkupMismatch` (never guessing) on anything unexpected (odd hl-code count, value/order mismatch, a phrase matching a repeated word at the wrong occurrence — the last one is a known open gap, see `docs/planning-log/2026-09-08-markup-aware-migration.md` section 6). **General lesson: before writing off `en` content as unencodable/blocked, check whether the "unencodable" shape is actually a solvable, already-established markup convention sitting unconsumed in the data**, not a translation-completeness gap — this project has now found that shape twice (this one, and the earlier prologue-echo `{{...}}` stripping case at `0x4efeb0`/`0x4f0000`).

**The "genuinely unsolved" mid-content icon/pen0/param8 bucket (~275 estimated) got a real mechanism — `text_encoder.derive_en_positional_markup()`/`encode_mixed_markup_stream()` (2026-09-08).** Real, fresh count: 270 `status:drafted` single-ref-site entries whose JP content (past `jp_prologue()`) carries an `icon`/`pen0`/`param8` code — see `docs/planning-log/2026-09-08-icon-pen0-markup-mechanism.md` for the full bucket breakdown, mechanism design, and 5 hand-verified byte-exact samples. Unlike `derive_en_hl_markup()` (needs word/phrase matching) or `derive_en_prologue_markup()` (substitution confined to the leading prologue, always renders first), this handles a control code positioned ANYWHERE — leading, trailing, mid-sentence, or scattered across multiple points — via EXPLICIT positional markers: the translator writes `{{HL:0xNNNN}}`/`{{PARAM:0xNNNN}}`/`{{ICON:0xNNNN}}` literally wherever in `en_text` the code should land (no word-matching ambiguity, since there's no text to match — the marker's own position IS the answer). Structurally validated against the JP source's FULL in-order `hl`/`icon`/`param8` sequence (prologue-classified or not, same "boundary isn't load-bearing" principle as `derive_en_hl_markup()`) — `MarkupMismatch` on any count/value/order mismatch, never guesses. `{{PARAM:}}`/`{{ICON:}}` are accepted interchangeably (matches real existing registry usage, e.g. `0x457c50` already uses `{{PARAM:0x7000}}` for a genuine `icon`-kind token) — which raw bytes get emitted is decided by the JP token's own real `kind`, not the tag spelling. A `pen0` token in the `0xE800`-`0xEFFF` sub-range is treated as hl-equivalent (`{{HL:}}` matches it too) — confirmed byte-identical to the `hl` OPEN_HL/CLOSE_HL shape per `dialog_codec.py`'s own module docstring. **Critical scope guard**: raises `MarkupMismatch` (refuses, never silently drops bytes) if content contains a true pen-position `pen0` token (cursor-movement, ~92% of raw `pen0` occurrences in the bucket — pen-X/Y-set, pen-Y-add, table-coord — genuinely NOT a value substitution, no established notation, a separate not-yet-built problem) or a mid-stream `setup` token. Width/pagination accounting is threaded with a new `zero_width_chars` parameter (`wrap_line()`/`layout_page_lines()`/`plan_page_chunks()`/`plan_stream_pages()`/`encode_stream()` all now accept it) so an `hl`-code placeholder (draws nothing) doesn't count against the character budget — confirmed load-bearing on a real sample (`0x457d60`: 25 naive chars vs 21 actual visible chars against a 22-char budget — the naive count would have wrongly triggered auto-wrap).

**Reviewed 2026-09-08 by 2 independent fresh Sonnet adversarial reviewers, both verdict SAFE WITH CHANGES NEEDED — 2 real findings, both fixed same pass, re-validated with zero regression (10/10 `ready_as_is` entries still byte-exact including `param8` payload):** (1) `zero_width_placeholders()` originally checked `kind == "hl"` only, silently excluding the hl-LIKE `pen0` sub-family (`0xE800-0xEFFF`) from the zero-width set — reproduced the exact over-counting bug the fix exists to prevent (confirmed live on real code `0xe832` at entry `0x478d30`); fixed to also match `pen0` in that range. (2) An hl-like open/close pair can be split across an auto-inserted PAGE boundary by `plan_page_chunks()`'s DP cost model (which has zero awareness that two placeholder characters are semantically paired) — reviewer built a concrete repro (a long hl-wrapped sentence auto-paginating hl-open onto page 0 and hl-close onto page 2) showing this would leave a highlight colour bleeding into subsequent pages (colour state persists across PAGE, no evidence it resets). Fixed by adding `_check_hl_pairs_single_page()`, called automatically at the end of `encode_mixed_markup_stream()`: decodes its own output and raises `EncodeError` if any hl-like pair spans more than one page, rather than shipping the bleed silently. Neither finding was live in the 10 `ready_as_is`/20 `needs_hl_backfill_mechanical` entries (short highlighted spans), but both are certain to be hit once the remaining ~178-entry not-yet-authored bucket gets markup — see `docs/planning-log/2026-09-08-icon-pen0-markup-mechanism.md` section 6/6b for full detail. Also flagged, not yet fixed: the `param8` payload-splice code path (`encode_label()`'s payload-emission branch) was verified correct in ISOLATION but has never been exercised end-to-end through the full `derive_en_positional_markup()`/`encode_mixed_markup_stream()` pipeline on a real `param8` token — low live risk today since all 12 `param8`-bearing bucket entries are separately gated `blocked_param8_semantics_unresolved`, but don't treat it as validated the way the `hl`/`icon` path is once that gate lifts.

**First real-world application, 2026-09-08 (live-verify follow-up session): 26 of 30 tagged-ready entries migrated and live-PINE-verified 26/26 MATCH** (`tools/migrate_midcontent_markup_30_2026-09-08.py`, 2 more independent adversarial reviewers, both verdict SAFE) — all 10 `ready_as_is` entries applied unchanged, plus 16 of 20 `needs_hl_backfill_mechanical` entries via a new `mechanical_hl_backfill()` helper (inserts the missing `{{HL:}}` wrap around an already-placed `{{PARAM:}}`/`{{ICON:}}` marker, using jp's own real hl-code values, matching markers to jp's value sequence by POSITION only — never reorders). **4 of the 20 correctly held back, not forced** — 2 (`0x4efe60`/`0x4efee0`) for a pre-existing PARTIAL `{{HL:}}` marker (open, no close) compounding with a separate known `jp`-completeness gap; 2 (`0x4596a0`/`0x4596d0`) for a genuine VALUE-ORDER mismatch the downstream `derive_en_positional_markup()` call catches (jp's real order is person-then-count, drafted `en`'s natural word order is count-then-person) — **exposing a real, narrow gap in `tag_midcontent_markup_shape_2026-09-08.py`'s own `classify()` heuristic**: when `en` has ZERO existing hl markers, `classify()` can't yet distinguish "just needs an hl wrap" from "needs an hl wrap AND has an order mismatch" (its `existing_markup_order_or_value_mismatch` bucket only triggers when en's TOTAL marker count already equals jp's, which requires hl markers to already be present) — a future pass touching that script should backfill-then-validate before tagging, the same discipline the migration script itself now applies. Both held-back pairs flagged to `docs/planning-log/OPEN-QUESTIONS-2026-09-08.md`, `status` left `drafted`. Reviewers separately confirmed: the sector-boundary loader-trigger-hook rebuild path (triggered since this batch pushed the sentinel blob from 103→105 sectors) is byte-identical to 2 already-shipped sibling scripts' own successful real applications of the same path; all 26 entries' encoded streams independently re-decoded and control-code-sequence-matched against the real JP source, including the trickiest id+delta case (`0x52f53c`, see above).

**`derive_en_positional_markup()` requires every marker's VALUE to appear in the SAME RELATIVE ORDER as the JP source's own stream — this is very likely a genuine safety property, not just strictness.** `icon` substitution is a self-contained 2-byte code with no stored args, so the runtime almost certainly resolves "what value goes here" from an ordered argument queue consumed in stream-encounter order (the code's own value plausibly only selects a rendering STYLE, not which argument) — meaning silently letting a translator reorder markers relative to JP could swap WHICH VALUE renders where (e.g. a count where a name belongs). Confirmed real on 4 already-drafted entries (`0x4596a0`, `0x4596d0`, `0x4f1720`, `0x4f1760`): natural English word order ("X got Y from Z") reordered which substituted value comes first relative to JP's own sentence structure ("X, from Z, got Y") — the mechanism correctly raises `MarkupMismatch` rather than guessing. This is UNCONFIRMED without a live disassembly trace of the substitution-queue consumer, but refusing is the responsible default either way. **Do not build a "smarter" backfill/migration tool that silently reorders markers to match translator wording** — route any `existing_markup_order_or_value_mismatch`-tagged entry to a human decision (rewrite EN to preserve JP's value order) instead.

**Open, real gap found validating this: TRUE `param8` (`0xb000`/`0x4800`/`0xd800` EXACT) payload semantics are NOT uniformly "opaque runtime value."** 2 independent real samples (`0x4592e0`/`0x459300`-family "category-submenu" menu-label chapters — `steal-command`/`discard-command`/`curse-command`/`prank-command`/`vocab-field-commands`/`board-event-ui-labels`) show the param8 payload is actually GLYPH-DECODABLE JAPANESE TEXT (e.g. payload bytes `a601d8010d010008` decode as `所`,`持`,`金`,LINE — literally "Gold" plus a line break) — a genuinely different mechanism (an inline, ≤4-character label field reusing the param8 byte-slot for real translatable content) from the icon-substitution shape this mechanism was built for. Mechanically, `derive_en_positional_markup()`/`encode_mixed_markup_stream()` will happily splice ANY param8 payload through verbatim (matches the established "re-derive fresh from JP, never invent" convention) — but for an inline-label entry, doing so would silently ship UNTRANSLATED text hidden inside what looks like an opaque value marker. **Do not migrate any true-param8 entry (`midcontent_markup_shape.readiness == "blocked_param8_semantics_unresolved"` after the 2026-09-08 tagging pass) without first checking, per-entry, whether its payload is glyph-decodable (inline label, needs translation) or genuinely opaque (safe to carry verbatim)** — a second sample (`0x47c9b0`) also showed suspicious payload bytes (resembling a coherent icon+hl+glyph+LINE continuation) that could NOT be confidently classified either way in the time available; treat as unresolved, not opaque-by-default.

**The `0x4efeb0`/`0x4f0000` "prologue-echo" shape got its own generalized, reusable function — `text_encoder.derive_en_prologue_markup(en_text, jp_tokens)` (2026-09-08).** For entries whose JP source's disqualifying `hl`/`icon` codes sit ENTIRELY inside `jp_prologue()` (an `icon` token there is usually a runtime name/value SUBSTITUTION marker, e.g. `0xa000`, distinct from `param8`'s 8-byte-payload family — see gap 2 above), `encode_stream()` already reproduces those codes verbatim, unconditionally, before ANY page content — so the substituted value ALWAYS renders first in the box, no way around it with this encoder (repositioning it would need the same kind of content-position machinery `hl_wraps` gives mid-content `hl`, generalized to standalone substitution codes — not built, a real, still-open gap, see `docs/planning-log/2026-09-08-markup-aware-migration.md`'s "Outstanding" section). `derive_en_prologue_markup()` therefore does not reposition anything — it recognizes the narrower case where `en_text` ALREADY commits to value-first wording (i.e. `en_text` starts with the exact `{{HL:0xNNNN}}...{{PARAM:0xNNNN}}` notation the real prologue tokens produce, through the LAST icon token — a trailing hl-close needs no en-side echo, it's silently reproduced regardless) and mechanically strips that known prefix so the remainder goes through the ordinary encoder unmodified. Raises `MarkupMismatch` (never guesses) if `en_text` doesn't already start value-first — **that is a translation/word-order decision, not a mechanical fix**; do not auto-rewrite wording to force this path, flag it for the translator instead (see `docs/planning-log/OPEN-QUESTIONS-2026-09-08.md` for a worked example of 15 entries flagged this way, vs. 9 siblings that already qualified mechanically and were migrated with zero wording change). Use the `encode_prologue_echo_stream()` wrapper, not `derive_en_prologue_markup()` directly — it also fixes a real leading-space-gets-stripped gap, see `skills/PATCH-MOD-ISO.md`'s prologue-verbatim-gaps entry, item 3.

### `id` + delta shifts
**A `code_immediate` entry's `lui`/`addiu` pair CAN legitimately reconstruct to `own_id + small_even_delta` rather than bare `own_id` — reviewed and trusted 2026-09-08, extending the pattern already established for `pointer_array`** (see the "stored pointer always equals the entry's own `id`" gotcha in `skills/PATCH-MOD-ISO.md`'s Hash-ledger section, 2026-09-05). Mechanism is the SAME regardless of `ref_type`: whether the address is a data-slot VALUE (`pointer_array`, read at runtime) or a compile-time CONSTANT baked into the instruction stream (`code_immediate`), either way it's simply the literal string-start address the code passes to the renderer — migrating is the identical repoint operation, just with "expected old value" corrected to `id+delta`. Always content-verify before trusting a shift (decode fresh at the shifted address, compare against the entry's own registered `jp`, exact match required) — a coincidental delta landing on unrelated neighboring content is a real failure mode this technique must rule out, not assume away (8 of 23 raw shift-shaped candidates found 2026-09-08 were exactly this — coincidental deltas, correctly excluded). A shift that reconstructs to a BOGUS (non-executing) `lui`/`addiu` pairing is a different, unrelated failure mode this check does NOT catch — see `0x535a1a`'s "branch-pairing false positive" in `docs/planning-log/2026-09-07-sentinel-ground-truth-recovery.md`.

**Follow-up 2026-09-08 (later the same day): the `0x53464e`/`0x534666`/`0x534692`/`0x5346aa` case above was investigated to a full, confirmed resolution — it turned out to be the SAME legitimate id+delta class after all, not a partial-overlap false positive, once decoded from the right source.** The earlier check decoded the shifted address on `iso/modded/modded-sentinel-bypass-fix.iso`, which already had a pre-existing, non-registry-tracked, ad-hoc in-place edit sitting at bare `id` (the actual bug — see below) — decoding the SAME shifted address on `iso/original/original.iso` instead gives a byte-exact match to the registered `jp`, 4/4, zero exceptions: the original JP string at each `id` begins with 1 (`0x53464e`/`0x534666`) or 3 (`0x534692`/`0x5346aa`) leading SPACE glyphs (`0x0000`) before the real content, and the live `ref_site` (`id+2`/`id+6`) has always correctly pointed PAST that padding — exactly the same mechanism as `0x52f53c` (there: stray zero-word padding; here: stray SPACE-glyph padding), just a different padding byte value. **Lesson generalized from this: when a shifted-address content-verify check fails against the CURRENT working ISO, also try the SAME check against `iso/original/original.iso` before concluding "partial-overlap false positive"** — the working ISO can itself hold stale/corrupted bytes at the address in question (from an earlier, non-registry-tracked edit) that the original never had. The real, separate bug this uncovered: some earlier, untracked edit had written the English replacement text directly in-place starting at bare `id` (2/6 bytes too early, not accounting for the leading-space-skip), leaving the game's real, unrepointed pointer reading a truncated tail ("ambler"/"onk"/"en"/"org") — a genuine, live rendering bug, fixed via the standard sentinel-relocation mechanism (same as this chapter's other ~22 already-patched siblings) in `tools/migrate_openquestions_2026-09-08.py`. See `docs/planning-log/2026-09-08-openquestions-followup.md` for the full derivation, independently reproduced by 2 adversarial reviewers before applying.

## Gotchas

**Gotcha confirmed 2026-09-08 — `midcontent_markup_shape.readiness` is scoped to ONE mechanism, not a general "can this entry be migrated" verdict.** All 9 `settings-option`-chapter entries are migratable via `text_encoder.encode_settings_stream()` (a different, pre-existing 2026-09-04 encoder purpose-built for this content class — no HDR, `<0xNNNN>`-verbatim-copy convention), regardless of what `midcontent_markup_shape.readiness` says — 6 of the 9 are tagged `blocked_true_pen0_position` by `tools/tag_midcontent_markup_shape_2026-09-08.py`, which is CORRECT for the generic icon/pen0 positional-markup mechanism that tag describes (it really does refuse true cursor-position pen0 codes) but says nothing about whether some OTHER, differently-scoped encoder can handle the same bytes. Before treating a `blocked_*`/`no_markup_yet`/etc. readiness tag as "this entry cannot be migrated," check whether the entry's chapter already has its own dedicated encoder (`encode_settings_stream()` for `settings-option`, `encode_class_tooltip_stream()` for tooltips, etc.) that was simply never in scope for the tagging script. **Bigger gotcha found 2026-09-09 — `midcontent_markup_shape` TAG ABSENCE is not evidence of anything, for a whole `ref_type`.** `tools/tag_midcontent_markup_shape_2026-09-08.py` unconditionally `continue`s (skips, never classifies) any entry with `ref_type == "struct_table_field"` (its own line 165) — so for that entire `ref_type`, missing the tag means "never run through the classifier," not "classified and found clean." See `docs/planning-log/2026-09-09-plain-drafted-batch1.md` and `OPEN-QUESTIONS-2026-09-08.md` section 7.

**THIRD distinct tag-absence root cause found 2026-09-09, in `board-event-ui-labels`/`battle-status-messages-1/2/3` — a prologue-vs-content SCOPE gap, not a `ref_type` skip-list or genuine markup-freedom.** `tools/tag_midcontent_markup_shape_2026-09-08.py` only tags an entry if its POST-PROLOGUE content contains an `icon`/`pen0`/`param8` token (`kinds_present & TARGET`, `TARGET = {icon, pen0, param8}` — `hl` alone doesn't count). 186 more `status:drafted`, no-tag entries in these 2 chapters were found to ALL carry real `hl`/`icon` markup — but every one has its ONE substitution (almost always a subject-name `icon:0xa000`) confined entirely to `jp_prologue()`, with post-prologue content carrying ONLY `hl`-wraps around literal words/phrases (status names, item names — not runtime substitutions).
